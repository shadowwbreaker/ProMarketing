# SUPPORT & DISPUTES — поддержка, жалобы и арбитраж

Статус: проектирование (Phase 0, 2026-11-07). Реализация — Phase 9, но модель данных и события закладываются с Phase 1/6.

## 1. Принципы FunPay и их адаптация

Источник — справочный центр FunPay (полный свод правил funpay.com отсюда недоступен; перед Phase 9 сверить вручную).

| Принцип FunPay | Как у нас |
|---|---|
| Деньги покупателя удерживаются, пока покупатель не подтвердит выполнение | Удержание у платёжного провайдера (escrow), а не на внутреннем балансе |
| Продавец может сам вернуть деньги кнопкой в интерфейсе | «Вернуть деньги» у продавца по позиции заказа — без участия поддержки |
| Администрация отменяет заказ, если продавец неактивен или стороны в споре | Таймер принятия заказа + решение администратора в споре |
| Задержка вывода 48 ч для защиты от мошенничества | Задержка выплаты после подтверждения (настраиваемая) + удержание на срок размещения (D-009) |
| Возврат на внутренний баланс FunPay | **Не переносим**: возврат только на исходный способ оплаты через провайдера (roadmap 7.5) |
| Ответ поддержки обычно в течение 48 ч, работа 24/7 | SLA очереди настраивается, отображается пользователю |
| При отмене заказа отзыв удаляется | Отзыв по отменённой/возвращённой позиции снимается с публикации (остаётся в истории модерации) |

## 2. Сущности

`SupportTicket`, `Dispute`, `DisputeParty`, `DisputeMessage`, `DisputeEvidence`, `DisputeReason` (справочник), `DisputeDecision`, `DisputeAction`, `RefundRequest`, `OrderEvent`, `AdminNote`, `UserSanction`, `PublicationCheck`. Поля — в `docs/DATABASE.md`.

Ключевое: спор привязан к заказу и к **набору позиций** (`DisputeItem`), а решение принимается по каждой позиции. Это обеспечивает частичные споры по сеткам.

## 3. Статусы спора и переходы

```
OPEN ─► WAITING_SELLER ─► UNDER_REVIEW ─► RESOLVED ─► CLOSED
  │          │                 │  ▲            │
  │          ▼                 ▼  │            ▼
  │     (таймаут) ──────► EVIDENCE_REQUESTED  APPEALED ─► UNDER_REVIEW
  │                            │
  └─► WAITING_BUYER ◄──────────┘
UNDER_REVIEW ─► ESCALATED ─► UNDER_REVIEW (старший администратор)
UNDER_REVIEW ─► REJECTED ─► CLOSED (или APPEALED)
```

Правила:
- Переходы — только через сервис `DisputeService.transition()` с проверкой разрешённого перехода, роли и обязательного комментария.
- Таймаут ответа стороны **не** закрывает спор автоматически в чью-либо пользу: переводит в `UNDER_REVIEW` с пометкой «сторона не ответила в срок» (roadmap 9.5).
- Апелляция — один раз, рассматривает другой сотрудник (`assignee != предыдущий`), затем `CLOSED` окончательно.
- Пока спор не закрыт: выплата по затронутым позициям заблокирована; сообщения и доказательства не редактируются.

## 4. Решения администратора

Каждое — `DisputeDecision` по позиции с обязательным комментарием, затем `DisputeAction` (исполнение):

| Решение | Действие системы | Зависит от провайдера |
|---|---|---|
| Полный возврат | `RefundRequest(amount = оплачено − уже возвращено)` | `partial_refund` не нужен |
| Частичный возврат | `RefundRequest(amount)` с проверкой лимита | `partial_refund` |
| Отказ в жалобе | Разблокировка выплаты | — |
| Повторное выполнение | Позиция → `IN_PROGRESS`, новый дедлайн | — |
| Продление срока | Новый дедлайн в `OrderEvent` | Срок сделки ≤ `max_hold_days` |
| Подтверждение в пользу продавца | Позиция → `COMPLETED`, выплата | `payouts_to_sellers` |
| Запрос доказательств | → `EVIDENCE_REQUESTED`, таймер стороне | — |
| Эскалация | → `ESCALATED`, назначение старшего | — |
| Санкции | `UserSanction` (предупреждение, ограничение, блокировка) | — |

Если возможности провайдера не позволяют действие, кнопка недоступна, а backend отклоняет запрос — без фиктивных внутренних операций.

## 5. Конфликтные сценарии (все 15 из roadmap 9.7)

Для каждого: что фиксирует система, что видит администратор, возможные решения, тест.

| # | Сценарий | Данные и механика | Возможные решения | Тест (Phase 9/14) |
|---|---|---|---|---|
| 1 | Продавец не отвечает | `last_seen` и время последнего сообщения сторон в заказе; таймер принятия заказа. До принятия покупатель может отменить заказ сам (полный возврат, без спора). После — жалоба с причиной «не отвечает»; таймер ответа продавца | Полный возврат; продление; санкция за игнорирование | Таймаут → `UNDER_REVIEW`, без автоматического возврата |
| 2 | Видео не опубликовано | Дедлайн публикации в условиях; отсутствие `PublicationProof` | Возврат; продление; повторное выполнение | Дедлайн прошёл, доказательств нет → решение «возврат» доступно |
| 3 | Не соответствует ТЗ | Сравнение доказательства с зафиксированной версией `OrderTermsVersion`; в карточке спора — ТЗ и публикация рядом | Исправление, повторное выполнение, частичный/полный возврат | ТЗ берётся из версии на момент оплаты |
| 4 | Видео удалено раньше срока | `placement_until` в условиях; `PublicationCheck` при публикации и проверка по требованию (D-010) | Компенсация из удерживаемой части (D-009); санкция | Проверка «не найдено» до `placement_until` → основание для жалобы |
| 5 | Выполнена часть сетки | Каждая позиция — отдельный `OrderItem` со своей ценой, статусом и доказательствами; спор по набору позиций | Решение по каждой позиции; частичный возврат = сумма невыполненных позиций | Сетка 5 акк., 3 выполнили → возврат ровно 2 позиций, выплата 3 |
| 6 | Покупатель не подтверждает | Окно подтверждения после доказательства; по окончании — разовая проверка публикации и автоподтверждение (или обращение продавца в поддержку, если проверка не прошла) | Подтверждение в пользу продавца | Нет действий покупателя + публикация доступна → `COMPLETED` |
| 7 | Ложная жалоба | История споров пользователя (доля отклонённых), доказательства продавца | Отказ; предупреждение/санкция покупателю при доказанном злоупотреблении | Отклонённая жалоба не снижает рейтинг продавца |
| 8 | Накрутка статистики | История `SocialAccountStatistics`, сигнал `SUSPICIOUS` антифрода, источник данных | Скрытие предложения до проверки; санкция; частичный возврат, если заказ основан на ложных данных | Подозрение → предложение скрыто, но не удалено |
| 9 | Цена изменена после оплаты | Цена зафиксирована в `OrderItem.price_minor` и версии условий; изменение цены предложения не влияет на оплаченные заказы | Отклонение требования доплаты; санкция | Изменение цены оффера не меняет оплаченный заказ |
| 10 | Сделка вне платформы | Жалоба с причиной 12; детектор контактов/реквизитов в чате формирует сигнал (не наказание) | Предупреждение, ограничение, блокировка | Сообщение с телефоном → сигнал модератору |
| 11 | ТЗ изменено после оплаты | Новые требования — только новая версия условий с согласием обеих сторон; иначе обязательна исходная | Решение по исходной версии | Несогласованная версия не становится действующей |
| 12 | Аккаунт продавца удалён/заблокирован | Разовая проверка доступности аккаунта (`check_data_availability`) при споре | Возврат; передача администратору | Недоступный аккаунт → спор `UNDER_REVIEW` |
| 13 | Платформа удалила видео | Причина, если доступна; условия заказа о рисках модерации платформ (поле в условиях) | По условиям заказа: возврат, повтор, отказ | Решение учитывает поле `platform_removal_policy` |
| 14 | Покупатель задержал материалы | Событие «материалы переданы» в `OrderEvent`; дедлайн продавца отсчитывается от него, если так в условиях | Пересчёт дедлайна; отказ в жалобе | Дедлайн сдвигается на задержку |
| 15 | Встречные претензии | Один спор на позицию, обе стороны — заявители; хронология событий в одной ленте | Решение по совокупности фактов | Вторая жалоба по той же позиции присоединяется к спору, а не создаёт новый |

## 6. Причины жалоб

Справочник `DisputeReason` — 13 причин из roadmap 9.2. Для каждой: кто может подать (покупатель / продавец), обязательные поля, рекомендуемые доказательства. Продавцу доступны свои причины: «покупатель не подтверждает», «покупатель не передал материалы», «покупатель требует сверх ТЗ».

## 7. Журнал администрации

`AuditLog` (append-only, хеш-цепочка): кто, когда, действие, объект (заказ/позиция/спор), статус до/после, причина, комментарий, IP. Просмотр карточки спора тоже логируется (доступ к персональным данным).

## 8. Настраиваемые сроки (значения по умолчанию — предложение)

| Параметр | По умолчанию |
|---|---|
| Принятие заказа продавцом | 24 ч |
| Ответ стороны в споре | 48 ч |
| Окно подтверждения покупателем после доказательства | 72 ч |
| Задержка выплаты после подтверждения | 48 ч |

Все значения — в настройках платформы, изменения логируются.
