## D-001 · 2026-11-07 · ACCEPTED · Стек

**Решение.** Модульный монолит:
- Backend: Python 3.12, Django 5 + Django REST Framework, drf-spectacular (OpenAPI).
- БД: PostgreSQL 16.
- Очередь задач: Redis + Celery (только разовые задачи и внутренние таймеры, см. D-004).
- Хранилище файлов-доказательств: S3-совместимое (локально MinIO).
- Frontend: Next.js (App Router) + TypeScript, Tailwind CSS, генерируемый из OpenAPI типизированный клиент.
- Dev-окружение: Docker Compose.
- Тесты: pytest + pytest-django + factory_boy; Vitest; Playwright для e2e.

**Обоснование.** Репозиторий пуст, ограничений совместимости нет. Django даёт зрелые авторизацию, ORM, миграции, транзакции и `select_for_update` (нужны для идемпотентности платежей и защиты от двойных возвратов), а также служебную админку для внутреннего использования на ранних этапах. Интерфейсы провайдеров в roadmap заданы в snake_case (`validate_profile_url()` и т. п.) — это естественно ложится на Python.

**Альтернатива.** NestJS + Prisma + Next.js (единый TypeScript). Тоже рабочий вариант; хуже — менее зрелые транзакционные примитивы ORM для финансовых сценариев.

## D-002 · 2026-11-07 · PROPOSED · Модульный монолит, а не микросервисы

Одна кодовая база backend, разделённая на Django-приложения с явными границами (`accounts`, `social_data`, `catalog`, `orders`, `payments`, `chats`, `notifications`, `support`, `reviews`, `audit`, `staff`). Межмодульное взаимодействие — только через сервисный слой модуля, а не через прямой доступ к чужим моделям. Выделение сервисов — по факту нагрузки, не заранее.

## D-003 · 2026-11-07 · PROPOSED · Основной способ получения статистики — OAuth владельца аккаунта

Продавец подключает аккаунт через официальный OAuth платформы (TikTok Login Kit, Instagram API with Instagram Login, Google OAuth для YouTube). Это одновременно:
1. разрешённый способ получения данных;
2. доказательство, что аккаунт принадлежит продавцу (защита от выставления чужих аккаунтов);
3. единственный официальный способ получить просмотры видео TikTok для коммерческого продукта.

Ручной ввод допускается только со статусом `MANUAL` и явной маркировкой в каталоге. Подробно: `docs/SOCIAL_DATA.md`.

## D-004 · 2026-11-07 · PROPOSED · Фоновые задачи: что можно и что нельзя

Разрешено в фоне:
- одна разовая задача получения статистики, созданная действием пользователя;
- внутренние таймеры заказов и споров (дедлайн принятия, окно подтверждения, срок ответа в споре, истечение сделки у провайдера);
- обработка webhook платёжного провайдера;
- удаление/обезличивание данных по требованиям политик платформ (например, правило 30 дней YouTube) — это удаление, а не сбор.

Запрещено: любые периодические задачи, которые обращаются к социальным платформам без действия пользователя или администратора по конкретному заказу/спору.

## D-005 · 2026-11-07 · PROPOSED · Деньги

- Суммы хранятся в минимальных единицах валюты (`BIGINT`, копейки/центы) + код валюты ISO 4217. Никаких `float`.
- Внутренний «баланс пользователя» не создаётся (roadmap 7.5). Есть только журнал финансовых операций, отражающий операции у провайдера.
- Каждая исходящая операция к провайдеру имеет ключ идемпотентности, сохранённый до вызова.
- Возвраты — на исходный способ оплаты через провайдера (отличие от FunPay, который возвращает на внутренний баланс).

## D-006 · 2026-11-07 · ACCEPTED (уточнено в D-016) · YouTube: среднее просмотров — производная метрика

Политики YouTube API запрещают показывать независимо рассчитанные (derived) метрики и агрегировать данные для третьих лиц без отдельного одобрения (с 2026-06-01 — через форму расширения квоты, Section 5, use case «Analytics & Reporting»). Без одобрения статистические данные нельзя хранить дольше 30 дней без обновления.

Предлагается:
1. Подать заявку на одобрение derived metrics до коммерческого запуска YouTube.
2. До одобрения YouTube-провайдер работает только в dev/staging; в каталоге YouTube-предложения показываются со статусом `UNAVAILABLE` или `MANUAL`.
3. Хранимые данные YouTube старше 30 дней — автоматически помечаются `STALE`, числовые значения скрываются из каталога и удаляются по правилу политики, пока владелец не нажмёт «Обновить».

Требует подтверждения (Q-05).

## D-007 · 2026-11-07 · ACCEPTED · Instagram — только профессиональные аккаунты

Официальный API Instagram не работает с личными аккаунтами. Продавец должен перевести аккаунт в Business/Creator. Age-gated аккаунты через Business Discovery не возвращаются. `view_count` Instagram включает платные и органические просмотры — это указывается в карточке.

## D-010 · 2026-11-07 · PROPOSED · Проверка публикации — только по событию

Наличие и доступность рекламного видео проверяется разово: (1) при отправке продавцом доказательства; (2) когда покупатель нажимает «Проверить публикацию» (с лимитом); (3) когда администратор проверяет спор; (4) один раз при окончании окна подтверждения и при окончании срока размещения. Это не мониторинг: количество проверок на заказ ограничено и связано с конкретными событиями заказа. Требует подтверждения вместе с D-004.

## D-011 · 2026-11-07 · PROPOSED · Неизменяемость условий заказа и доказательств

- Условия заказа сохраняются как версионированный снимок (`OrderTermsVersion`). После оплаты новая версия создаётся только с согласием обеих сторон; исходная версия не изменяется.
- Сообщения чата и доказательства: редактирование создаёт новую ревизию, удаление — мягкое; после открытия спора редактирование/удаление запрещено. Для файлов хранится SHA-256.
- `AuditLog` и `OrderEvent` — только добавление (append-only): запрет `UPDATE/DELETE` на уровне прав БД-роли приложения и цепочка хешей записей.

## D-012 · 2026-11-07 · PROPOSED · Роли

Единая модель ролей сразу на Phase 2 (а не на Phase 10), чтобы не переделывать RBAC: `buyer`, `seller` (могут совмещаться), `support_agent`, `moderator`, `admin`, `super_admin`. ## D-013 · 2026-11-07 · ACCEPTED · Первоначальный рынок — РФ

Платформа сначала запускается для рынка РФ. Последствия:

- кандидаты в провайдеры — ЮKassa и Т-Бизнес (Q-03);

## D-014 · 2026-11-07 · ACCEPTED · Выплата продавцу: полная, после 48 часов с подтверждения

Порядок:
1. Продавец публикует рекламу и отправляет доказательство.
2. Покупатель проверяет и подтверждает выполнение позиции заказа.
3. С момента подтверждения позиция получает статус выплаты `HOLD` и отсчёт `PAYOUT_HOLD_HOURS` (по умолчанию 48 ч).
4. Если за это время открыт спор по позиции — выплата `SUSPENDED` до решения спора.
5. Если спора нет — выплата `AVAILABLE`: продавец может вывести деньги (или выплата инициируется автоматически — настраивается).

Деньги в период ожидания находятся **у платёжного провайдера** (безопасная сделка/escrow), а не на внутреннем балансе. Начисление «к выплате» в интерфейсе — отображение состояния сделки у провайдера, а не хранение денег платформой. Требование к провайдеру (Q-03): удержание средств минимум до подтверждения + 48 ч, возможность возврата до выплаты, выплата по команде платформы.

**Принятый риск R-01.** После выплаты (через 48 ч) нарушения обязательного срока размещения (сценарий 4 — удаление видео раньше срока) нельзя компенсировать из удержанных средств. Доступно: спор, добровольный возврат продавцом, санкции, снижение репутации. Это отражено в правилах споров (`docs/SUPPORT_AND_DISPUTES.md`).

## D-018 · 2026-11-07 · PROPOSED · Отчёт по просмотрам после публикации (Phase 13)

Roadmap требует отчёты через 24 ч, 7 и 30 дней, но запрещает скрытый мониторинг. Правила:
1. Отчёт включает **покупатель** при оформлении заказа (флажок `results_report`, по умолчанию выключен) — это и есть запрос пользователя.
2. На одну позицию заказа планируются **ровно три** разовые проверки одного видео (24 ч, 7 д, 30 д от публикации). Они не переносятся, не повторяются и не продлеваются.
3. Только официальный API; при полном возврате, отмене или отсутствии ссылки проверка пропускается.
4. Глобальный выключатель — `RESULTS_REPORTS_ENABLED`.
5. Для YouTube это сырые просмотры одного видео, показанные покупателю этого размещения (не производная метрика канала). Хранение — по правилам D-016.

Требует подтверждения пользователя: если отчёты не нужны, достаточно `RESULTS_REPORTS_ENABLED=false`.

## D-019 · 2026-11-08 · ACCEPTED · Мастер добавления аккаунта, профиль, сообщения до оплаты

Решения пользователя после ручной проверки:
1. **Мастер «Добавить аккаунт»:** платформа (выпадающий список) → ссылка → статистика (подписчики, среднее по последним 15 видео) → объявление (название, формат, условия, срок выполнения, срок размещения, цена) → «Создать» (объявление публикуется в каталоге, если выполнены условия публикации).
2. **YouTube** — только ссылка на страницу Shorts (`https://www.youtube.com/@канал/shorts`, кириллические handle поддерживаются). Данные — YouTube Data API. Среднее для покупателей — по D-016 (продавец видит сразу).
3. **TikTok — оба варианта:** вход через TikTok (официальный API, подтверждает владение) и ручной ввод с пометкой «Вручную». Получение статистики по ссылке без входа владельца не делаем: официального API нет, а парсинг обходит защиту TikTok (запрещено в Phase 0).
4. **Instagram** — показан в списке как «недоступно» (реклама в сервисах Meta запрещена в РФ с 01.09.2025; D-013).
5. **Публичный профиль** по образцу FunPay: шапка, онлайн-статус, дата регистрации, рейтинг с распределением оценок, предложения по платформам, отзывы. Клик по нику открывает меню (профиль, кабинет, настройки).
6. **Сообщения до оплаты** («напишите продавцу перед оплатой»): отдельные диалоги между пользователями (`DirectThread`), те же правила против обхода платформы, что в чате заказа (сигнал модератору и предупреждение при контактах/реквизитах). После оплаты общение идёт в чате заказа.

## D-020 · 2026-11-08 · ACCEPTED · Подтверждение владения YouTube-каналом кодом в описании

1. Продавец нажимает «Получить код» (`PM-XXXXXX`), вставляет его в описание канала в YouTube Studio и нажимает «Проверить».
2. Проверка — один запрос `channels.list` (официальный YouTube Data API) на одно нажатие, лимит 20 проверок в час. Мониторинга нет.
3. После успеха `ownership_verified=true`, код стирается, его можно удалить из описания. Событие пишется в аудит.
4. В каталоге и профиле подтверждённые аккаунты отмечены «✓ владение подтверждено». Публикация без подтверждения не запрещена (решение можно ужесточить).
5. TikTok подтверждается входом через TikTok (OAuth); ручной ввод остаётся неподтверждённым.

6. **Передача канала настоящему владельцу (2026-11-08).** Если канал уже добавил другой пользователь без подтверждения, при добавлении владелец видит «Это мой канал — получить код», вставляет код в описание и проверяет. При успехе аккаунт переходит к нему: подтверждён, снят с публикации, прежние предложения выключены, аккаунт удалён из сеток прежнего продавца, прежний продавец получает уведомление, всё пишется в аудит. Если по аккаунту идут заказы — передача только через поддержку. Подтверждённый аккаунт забрать нельзя.

## D-021 · 2026-11-08 · ACCEPTED · Интерфейс по образцу FunPay, «канал» вместо «аккаунт»

Решения владельца после ручной проверки:
1. **Термин.** Аккаунт соцсети в интерфейсе и сообщениях об ошибках называется **«канал»** («Добавить канал», «Мои каналы», «Каналы сетки»). «Аккаунт» остаётся только для учётной записи пользователя на ProMarketing (вход, регистрация, пароль). В коде и API имена (`social_account`, `/catalog/accounts`) не меняются.
2. **Шапка:** Каталог · Покупки · Сообщения (со счётчиком непрочитанных) · Избранное · уведомления · меню пользователя. Сообщения — отдельная страница `/messages` в три колонки (список переписок, переписка, сведения о собеседнике). Избранное — отдельная страница `/favorites`.
3. **Убрано из кабинета:** «Избранное» (переехало в шапку), «Сообщения» (в шапку), «Просмотренные» (убрано совсем; история просмотров по-прежнему учитывается в рекомендациях).
4. **Каталог:** шапка с описанием защиты сделки, круги разделов (все каналы / TikTok / YouTube Shorts / сетки, размер по количеству), переключатели «Только продавцы онлайн» и «Данные платформы», поиск, кнопка «Фильтры» (панель сверху), «Продать рекламу»; список строками: описание · подписчики · просмотры · продавец (фото, онлайн, звёзды, время на сайте) · цена; сортировка по заголовкам.
5. **Страница объявления — «Оформление заказа»:** канал, краткое описание, статистика, подробное описание, выбор формата рекламы, «Купить за …», пояснение о защите оплаты, рейтинг продавца; справа — чат с продавцом.
6. **Тема:** только светлая, фон страниц белый.

## D-022 · 2026-11-08 · ACCEPTED · Упрощение и собственный стиль

1. **Убрано по решению владельца:** сравнение каналов (страница, кнопки, API `/catalog/compare`), рекомендации (`/me/recommendations`), просмотренные (`/me/viewed`), история действий в кабинете (`/me/activity`; журнал аудита для сотрудников не затронут). Таблица `insights_viewedoffer` оставлена без изменений — удаление данных только с отдельного разрешения; в неё больше ничего не пишется.
2. **«Мои покупки»** — отдельная страница `/purchases` в шапке. Кабинет: Продажи (каналы, продажи, сетки, выплаты, аналитика), Общение (уведомления, обращения), Прочее (настройки, отзывы, пригласить друга).
3. **Собственный стиль, чтобы не выглядеть копией FunPay:** знак ProMarketing (вертикальный кадр 9:16 с кнопкой воспроизведения, градиент розовый → фиолетовый); мотив «веер вертикальных роликов» с карточками статистики вместо круга с картинкой; плитки разделов вместо кругов; аватары-«сквиркл» вместо круглых; цена в «пилюле», подсвечивается при наведении; сообщения пузырями; липкая полупрозрачная шапка с активным пунктом на подложке; подвал.
4. **Анимации** (значения из `.claude/skills/better-ui`): появление страницы 300 мс (прозрачность, сдвиг 12px, размытие 4px), ступенчатое появление блоков (100 мс) и строк (30 мс, не дольше 180 мс), скелетоны при загрузке, появление меню (масштаб 0.96 → 1), нажатие кнопки 0.96, плавное «парение» декоративных кадров, панель фильтров. При системной настройке «уменьшить движение» остаётся только смена прозрачности.
5. **Главная:** только суть — что это, две кнопки (найти канал / продать рекламу), как проходит сделка (4 шага), 5 популярных каналов, блок для авторов.

## D-023 · 2026-11-09 · ACCEPTED · Уведомления, безопасность аккаунта, ссылка на канал

1. **Уведомления в интерфейсе убраны** (колокольчик и вкладка). О новых личных сообщениях говорит красная точка над «Сообщения» в шапке. Письма о ключевых событиях заказа и выплат продолжают отправляться на email; системные события заказа видны в чате заказа.
2. **Вкладка «Безопасность»** в кабинете: смена пароля (остальные сеансы завершаются) и двухфакторная защита. **Имя пользователя после регистрации не меняется** — ни в интерфейсе, ни через API.
3. **Ссылка на канал** обязательна при добавлении канала (как и раньше) и теперь видна везде: в каталоге и профиле `@канал ↗` открывает канал на платформе, на странице объявления — карточка «Открыть в TikTok/YouTube Shorts ↗», в мастере ссылка показывается на шаге объявления.
4. Проверка безопасности, производительности и устойчивости — `docs/TEST_REPORT_2026-11-09.md`.
