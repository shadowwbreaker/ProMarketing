# Техническая поддержка в Beta-tex

Локальный стенд Docker Compose использует проект promarketing-beta-tex. В рабочей копии Beta-tex сохранены код и эта инструкция для ручной проверки.

| Страница | Что проверить |
| --- | --- |
| http://localhost:3000/support | Выбрать тему и описать вопрос. Для проблемы с заказом указать номер и выбрать причину жалобы |
| http://localhost:3000/support/tickets | Открыть через выпадающее меню профиля. Список отсортирован от новых к старым. Обычное обращение открывается как переписка, жалоба открывается в заказе |
| http://localhost:3000/support/login | Войти сотрудником и попасть в очередь «Запросы» |
| http://localhost:3000/staff/tickets | Отфильтровать обращения по одной из трёх категорий. Открыть карточку с причиной, исходным сообщением и ссылкой на заказ |
| http://localhost:3000/staff/orders/search | Найти заказ по номеру. Из карточки обращения ссылка ведёт сразу к чату заказа и действиям поддержки |
| http://localhost:3000/staff/orders | Очередь «Заказы» для роли «Арбитраж». Нажатие назначает заказ, забирает его из очереди и открывает подробную карточку |
| http://localhost:3000/staff/orders/[id] | Назначенный арбитр видит заказ, историю, доказательства и может выполнить полный или частичный возврат либо закрыть обращение |
| http://localhost:3000/staff/support/roles | Войти владельцем и назначить роль «Администратор», «Техническая поддержка» или «Арбитраж» по подтверждённому email |

Локальные демо-аккаунты используют пароль Demo-password-1. Покупатель — demo-buyer@example.com, исполнитель — demo-seller1@example.com, сотрудник поддержки — demo-support@example.com, администратор — demo-admin@example.com, владелец — demo-owner@example.com, арбитр — demo-arbitrator@example.com. Оплата на стенде тестовая.

Для привязки личной учётной записи зарегистрируйтесь с адресом владельца, заданным в SUPPORT_OWNER_EMAIL. Откройте одноразовую ссылку из почтовых логов локального backend и войдите снова через служебную страницу. Только подтверждение по ссылке или завершённый сброс пароля оставляет в журнале доказательство владения адресом. При следующем входе сервер выдаёт владельцу роль. При будущей публикации настройте SUPPORT_OWNER_EMAIL на сервере. Для публичного окружения действует существующее требование TOTP.

Кнопка «Пожаловаться» в заказе ведёт в ту же форму, что и «Помощь». Тема и номер уже подставлены. Причины зависят от того, кто подаёт жалобу, покупатель или продавец. Можно указать позиции заказа и приложить доказательства. Отправка создаёт обращение в поддержку. Для жалобы по заказу сохраняются действующие правила приостановки вывода по спорным позициям. Служебный вход доступен по прямой ссылке и из служебного раздела для гостя.

## Поведение и права

- Короткий номер — первые восемь знаков существующего UUID заказа. При совпадении коротких номеров в форме можно использовать полный UUID со страницы заказа. Для темы «Проблема с заказом» номер и причина обязательны. В остальных темах номер можно указать при необходимости.
- Все обращения поддержки начинаются с одинаковой карточки. Фильтр показывает «Возврат средств», «Жалоба на продавца или покупателя» и «Прочее». Причина и исходный текст заявки доступны до назначения.
- Из карточки с заказом кнопка открывает чат заказа, где назначенный сотрудник может передать запрос арбитражу или закрыть его без возврата. Для старой заявки без привязки к спору передача создаёт дело по заказу либо добавляет переписку к единственному действующему делу.
- Передача убирает запрос из обеих вкладок поддержки. В «Заказах» арбитр берёт дело нажатием на строку. Дело перемещается в «Мои заказы». Второе назначение блокируется сервером. Новый возврат требует роли «Арбитраж» и назначения. Отказ и ожидание провайдера оставляют дело открытым.
- В заказе поддержка просматривает только переписку данного заказа. Старые сообщения загружаются страницами. Ответ сотрудника получает метку «Техническая поддержка» и виден покупателю и исполнителю. Назначения, ответы и закрытие записываются в журнал.
- Панель и её API доступны ролям поддержки и администрации. Управление ролями доступно главному администратору. Назначение по email сохраняет остальные роли пользователя. Клиентская настройка профиля не даёт прав сотрудника.

## API

| Маршрут с префиксом /api/v1 | Назначение |
| --- | --- |
| GET /support/topics | Темы формы и фильтра |
| GET /support/order-options?number=номер | Причины жалобы для стороны заказа и позиции собственного заказа |
| GET, POST /support/tickets | Список собственных заявок и жалоб, создание обращения выбранного типа |
| GET, POST /support/tickets/{id} | Просмотр собственной заявки и ответ |
| GET /staff/tickets?scope=queue или scope=mine | Обращения и жалобы в общей очереди или свои назначения с пагинацией и фильтром group: refund, complaint, other |
| GET /staff/tickets/{id} | Просмотр незанятой или своей заявки |
| POST /staff/tickets/{id}/{assign,reply,close,priority,refer} | Действие сотрудника |
| PUT /staff/support/roles | Назначение или отзыв роли по подтверждённому email |
| GET /staff/arbitration | Очередь арбитража и назначенные дела с scope=mine |
| POST /staff/arbitration/{id}/claim | Назначить дело текущему арбитру |
| GET /staff/disputes/{id}, POST /staff/disputes/{id}/{decide,close} | Карточка и действия назначенного арбитра |
| GET /staff/orders?q=номер | Поиск по короткому или полному номеру |
| GET, POST /orders/{id}/chat | История и сообщения заказа, курсор before для предыдущей страницы |

Миграция support.0004_arbitration_queue добавляет дату передачи и связь обращения с арбитражем. Уже открытые дела доступны в поддержке. Ранее эскалированные дела и апелляции попадают в очередь арбитров. Для повторного запуска выполните из рабочей копии Beta-tex.

    docker compose -p promarketing-beta-tex -f infra/docker-compose.yml up -d --build

Чтобы прочитать локальное письмо с подтверждением, откройте логи.

    docker compose -p promarketing-beta-tex -f infra/docker-compose.yml logs --tail=100 backend

## Итоговая проверка очереди и арбитража — 17 ноября 2026

Работа остаётся в локальной ветке Beta-tex. Коммитов и публикаций не выполнено; beta, main и Vercel не изменены. Рабочая копия: ProMarketing-beta-tex. Docker Compose: promarketing-beta-tex.

Реализован единый вход для всех обращений сотрудников. Категории фильтра: «Возврат средств», «Жалоба на продавца или покупателя», «Прочее». Карточка показывает причину, исходный текст и переписку. Для запроса с заказом сотрудник открывает чат заказа, закрывает запрос без возврата либо передаёт арбитражу. Передача исключает дело из общей и личной очередей поддержки.

В разделе арбитража нажатие на строку атомарно назначает дело текущему арбитру. Оно исчезает из общей очереди, остаётся в «Моих заказах» и открывается в подробной карточке. Другой арбитр не может забрать назначенное дело. Поддержка не получает право возврата. Участник заказа не может быть его арбитром. Главный администратор имеет права новой роли.

Финансовое решение остаётся незавершённым до подтверждения провайдера. На время ожидания повторное решение и закрытие блокируются. Отказ провайдера оставляет позицию в споре, чтобы арбитр мог повторить действие. При успешном частичном возврате остаток средств сохраняет установленное ожидание выплаты. На локальном стенде используется mock-провайдер: реальные деньги не списываются и не возвращаются.

## Дополнение: права поддержки, управление ролями и футер

Выполнено только в локальной Beta-tex, без коммита, переноса в beta и публикации в Vercel.

- Техническая поддержка получила право moderation.content: просмотр отзывов, скрытие, восстановление и рассмотрение жалоб. В служебном меню доступна ссылка «Модерация отзывов». Это право не даёт управление ролями, арбитражем или статистикой каналов.
- Главный администратор выбирает пользователя в разделе «Пользователи»: поиск по имени/email → карточка → «Управление ролями». Отмеченные роли назначаются, снятые отметки отзывают роль после сохранения. Отображаются текущие роли с понятными русскими названиями. Поддерживаются роли покупателя, продавца, поддержки, арбитра, модератора, администратора и главного администратора.
- Для сохранения нужен комментарий. Изменение проходит через существующий PUT /api/v1/staff/users/{id}/roles с проверкой user.manage_roles и аудитом. Форма доступна только главному администратору. Сохранены запреты на снятие роли с владельца и понижение главным администратором самого себя. У пользователя должна оставаться хотя бы одна роль.
- Форма по email сохранена. Из неё можно перейти к выбору пользователя; ссылка «Роли сотрудников» перенесена в общую служебную навигацию.
- С главной страницы убрана надпись «Комиссия 5%».
- Футер содержит единственный набор ссылок: «Каталог», «Пользовательское соглашение», «Правила», «Политика конфиденциальности». Ссылки «Помощь» и «Документация» из футера удалены, нижний дублирующий ряд кнопок убран. Страницы документов продолжают открываться по /terms и /privacy.

Для ручной проверки:
1. Войти demo-support@example.com и открыть «Модерация отзывов».
2. Войти demo-owner@example.com → «Пользователи» → выбрать пользователя → отметить или снять нужную роль → написать комментарий → «Сохранить роли».
3. Проверить главную страницу и футер на широком и узком экранах.

Автоматизация: frontend/e2e/staff-customization.cjs проверяет главную и футер, ссылки документов, доступ поддержки к отзывам, отсутствие формы ролей у поддержки и назначение/отзыв арбитража из выбранной карточки. Проверяется сохранение после перезагрузки и отсутствие горизонтальной прокрутки.

При проверке на промежуточной ширине обнаружено переполнение шапки длинным именем. Меню профиля теперь может сжиматься, имя сокращается многоточием; кнопка имеет полное доступное имя. Это сохраняет доступ к профилю на узком экране.

Для эмуляции увеличения 200% используется эффективная область 640 CSS-пикселей с deviceScaleFactor=2 для окна 1280 физических пикселей. CSS-свойство body.zoom не заменяет масштаб браузера, так как не пересчитывает media queries. Дополнительно проверяются реальные ширины 320, 375, 640, 768, 1024 и 1280 CSS-пикселей.
