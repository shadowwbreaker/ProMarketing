# PAYMENTS — внешняя платёжная интеграция

Статус: проектирование (Phase 0, 2026-11-07). Провайдер не выбран. Реальные платежи запрещены без отдельного разрешения пользователя.

## 1. Принципы

- Собственная платёжная система не создаётся. Деньги хранит и движет только провайдер.
- Внутренний журнал (`FinancialLedgerEntry`) лишь отражает операции провайдера; внутреннего «баланса» пользователей нет.
- Заказ считается оплаченным только после подтверждения от провайдера (проверенный webhook **и/или** запрос статуса), а не по возврату пользователя на страницу успеха.
- Нельзя обещать гарантированный возврат или удержание, пока не подтверждены возможности провайдера (roadmap 7.5).

## 2. Интерфейс адаптера

```python
class PaymentProvider(Protocol):
    code: str
    capabilities: ProviderCapabilities  # флаги ниже

    def create_payment(self, order_id, amount_minor, currency, idempotency_key, return_url) -> PaymentSession
    def get_payment_status(self, provider_payment_id) -> PaymentStatus
    def verify_webhook(self, headers, raw_body) -> VerifiedEvent   # бросает исключение при неверной подписи
    def request_refund(self, provider_payment_id, amount_minor, idempotency_key, reason) -> Refund
    def get_refund_status(self, provider_refund_id) -> RefundStatus
    def request_payout(self, seller_payout_ref, amount_minor, idempotency_key) -> Payout   # если capabilities.payouts
    def get_payout_status(self, provider_payout_id) -> PayoutStatus
```

`ProviderCapabilities` — флаги, от которых зависит бизнес-логика арбитража:
`marketplace_split`, `escrow_hold`, `max_hold_days`, `payouts_to_sellers`, `multiple_payouts_per_deal`, `partial_refund`, `multiple_refunds`, `pause_payout_on_dispute`.

Если флаг выключен, соответствующее решение администратора в арбитраже недоступно в интерфейсе и отклоняется backend — система не подменяет его внутренним балансом.

## 3. Идемпотентность и защита от повторов

- Входящие webhook: таблица `PaymentWebhookEvent` с уникальным индексом `(provider, provider_event_id)`. Повтор → `200 OK` без повторной обработки.
- Исходящие операции: ключ идемпотентности создаётся и сохраняется в БД **до** вызова провайдера, передаётся провайдеру.
- Двойной возврат/выплата: в транзакции блокируется `OrderItem`; проверяется, что сумма уже выполненных и ожидающих возвратов + новая ≤ оплаченная сумма позиции. Ограничение дублируется `CHECK`-условием и сверкой с провайдером.
- Сверка: при неизвестном исходе (таймаут) операция остаётся `PENDING_RECONCILIATION`, повторно не отправляется до запроса статуса.

## 4. Mock-провайдер (Phase 1–6)

`MockPaymentProvider` — полноценная эмуляция для тестов: платёж (успех/отмена/ошибка), подписанный HMAC webhook, повторная доставка события, неупорядоченные события, частичные и множественные возвраты, выплаты, сбой выплаты, таймаут. Возможности настраиваются, чтобы прогонять арбитраж при разных `capabilities`.

Защита: при `ENV=production` регистрация mock-провайдера вызывает ошибку старта.

## 5а. Модель выплаты (D-014, утверждено)

`подтверждение покупателем → HOLD (48 ч) → AVAILABLE → PAYOUT_REQUESTED → PAID_OUT`; при споре в период HOLD → `SUSPENDED` до решения. Деньги всё это время у провайдера. Обязательные возможности провайдера: `escrow_hold` (≥ срок исполнения + 48 ч), `payouts_to_sellers`, `partial_refund` (для сеток), `refund_before_payout`. Если провайдер их не поддерживает — это блокер, а не повод вводить внутренний баланс.

Комиссия 5% (D-015) рассчитывается и фиксируется в позиции при оплате: `fee = floor(price × 500 / 10000)`, `payout = price − fee`.

## 6. Связь с заказом

- Одна оплата на заказ; сумма распределяется по `OrderItem` (для сеток). Возвраты и выплаты ведутся **по позициям** — это основа частичного возврата при частично выполненной сетке.
- Статусы платежа, возврата, выплаты — отдельные сущности и отдельные машины состояний, не поля заказа.
- При открытом споре по позиции выплата по ней блокируется на уровне сервиса (и у провайдера, если `pause_payout_on_dispute`).

## 7. Реализация (2026-11-07)

| Компонент | Файл |
|---|---|
| Интерфейс и возможности провайдера | `backend/payments/providers/base.py` |
| Mock-провайдер (только dev/test) | `providers/mock.py` |
| Сервис: платёж, webhook, сверка, возвраты, выплаты | `payments/services.py` |
| API | `POST /orders/{id}/pay`, `POST /payments/webhooks/{provider}`, `GET /me/payouts`, `POST /me/payouts/{id}/withdraw`, `POST /me/payouts/{id}/retry`, dev: `POST /payments/mock/{id}/complete` |
| Таймер выплат | `payments.tasks.release_payouts` (каждые 10 мин) |

Правила: заказ оплачен только после подписанного webhook и подтверждения статуса у провайдера; неверно подписанные события не сохраняются; ключ идемпотентности записывается до вызова провайдера; таймаут переводит операцию в `pending_reconciliation` без повтора; возврат после выплаты отклоняется (R-01). При частичном возврате выплата пересчитывается: `(цена − возврат) − 5%`.

Чтобы подключить реального провайдера: реализовать `PaymentProvider` (например, `providers/yookassa.py`), заполнить `capabilities` по документации и договору, зарегистрировать в `providers/registry.py`, проверить `supports_d014()`.
