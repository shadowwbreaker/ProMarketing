# SECURITY

Статус: реализовано в Phase 1–12 (2026-11-07), кроме пунктов, отмеченных «не сделано».

## 1. Аутентификация и сессии
- Пароли: Argon2id (Django `Argon2PasswordHasher`), проверка по списку утёкших паролей.
- Сессии: серверные, cookie `HttpOnly`, `Secure`, `SameSite=Lax`; ротация при входе; выход со всех устройств.
- Подтверждение email, восстановление пароля — одноразовые токены с коротким сроком.
- 2FA (TOTP) — обязательно для сотрудников с финансовыми правами.

## 2. Авторизация
- RBAC через разрешения (DECISIONS D-012), проверка только на backend.
- Объектный доступ: каждый запрос к заказу/чату/спору проверяет участие пользователя или разрешение сотрудника. Тесты на доступ к чужим объектам обязательны.
- Финансовые действия — отдельное разрешение + журнал.

## 3. Веб-уязвимости
- SQL Injection — только ORM/параметризованные запросы.
- XSS — экранирование по умолчанию, санитизация пользовательского HTML (не разрешать HTML в чате), CSP.
- CSRF — Django CSRF для cookie-сессий.
- Rate limiting — вход, регистрация, сообщения, жалобы, обновление статистики, проверки публикаций.
- Внешние ссылки — валидация домена по платформе, `rel="noopener noreferrer nofollow"`, без серверных запросов на произвольные URL (защита от SSRF).

## 4. Файлы
- Ограничение типов и размера, проверка сигнатуры, антивирусная проверка, хранение вне веб-корня, выдача через подписанные ссылки, SHA-256 для доказательств.

## 5. Платежи
- Проверка подписи webhook, проверка источника, идемпотентность, сверка статуса с провайдером, защита от двойных возвратов/выплат (см. PAYMENTS.md §3).
- Mock-провайдер запрещён в production (проверка при старте).

## 6. Секреты
- Только переменные окружения/хранилище секретов. `.env` не коммитится, Claude его не создаёт и не изменяет без разрешения; шаблон — `.env.example`.
- OAuth-токены соцсетей шифруются в БД.

## 7. Персональные данные
- Минимизация, доступ сотрудников по разрешению и с журналом просмотра.
- Удаление по запросу пользователя; для данных YouTube — в течение 30 дней (политика YouTube API).
- Если рынок РФ — требования 152-ФЗ (локализация, согласия) — решение Q-01.

## 8. Аудит и антифрод
- `AuditLog` append-only с хеш-цепочкой.
- Антифрод формирует сигналы для проверки, а не наказания (roadmap Phase 12).

## 10. Финальный security review (Phase 15, 2026-11-07)

| Проверка | Результат |
|---|---|
| `manage.py check --deploy` (prod) | только W021 — HSTS preload выключен намеренно до подготовки домена |
| Отказ старта prod при небезопасной конфигурации | dev/короткий ключ, `PAYMENT_PROVIDER=mock`, `SOCIAL_PROVIDER_MODE=fake`, нет `FIELD_ENCRYPTION_KEY`, нет S3, консольный email — тесты |
| pip-audit `requirements.txt` | 0 уязвимостей |
| npm audit (production) | 0 уязвимостей после обновления Next.js 15.5.4 → 15.5.29 (было: критическая RCE в React flight protocol и ряд DoS/SSRF) и `overrides.postcss ^8.5.32` |
| npm audit (dev) | остаются уязвимости в vitest 3 / tinypool (только тестовый запуск, в образ не попадают). Обновление до vitest 4 упирается в ошибку npm 10.9 (`edgesOut`) — задача на обновление инструментов |
| Секреты в репозитории | не найдены; пароли только в `seed_demo` (демо-данные, команда не используется в prod) |
| Контейнеры | backend и frontend запускаются не от root; только Caddy публикует порты 80/443 |
| Служебный доступ | RBAC + обязательная 2FA + журнал аудита с проверкой целостности |

Остаточные риски: `'unsafe-inline'` в CSP; нет антивируса для вложений (хук `scan_status` готов); реальный платёжный провайдер не проверен (Q-03).
